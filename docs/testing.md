# Testing

`temple_index/{stateSlug}` holds at most 400 entries so a shard stays under Firestore's 1 MiB document limit. Text fields on each entry are trimmed to fixed lengths. The admin save refuses the 401st temple in a state and shows that message on the form; the write does not happen. Splitting one state across more than one shard is a later change. Do not raise the cap to fit a larger state.

Browse, search, and home read server `meta/temple_index`, then only the shards whose stamp differs from the stamp this device last applied (`SharedPreferences`). The full `temples/{id}` document loads on the detail screen, using the default Firestore source with a timeout and a cache fallback. `collection('temples')` runs only when the server confirms that meta document is missing or its shard map is empty. A timeout or other error serves the applied shards from the local cache when they exist, otherwise the bundled sample, and the next launch tries again. That path prints `index_fallback:` plus `index-cache` or `sample` in release builds. Web launches are always cold: the web Firestore cache is memory-only, so a new page load has no shard documents even when the applied stamps are still stored, and each shard is read from the server. Android and iOS set explicit Firestore settings before the first read: persistence on, cache size 100 MiB. That keeps the cache-first index if the SDK default changes. Web persistence stays off, so a reload stays cold. An offline banner shows when the device has no network and clears when a network returns; the directory already on screen stays up, and Home refreshes in the background without a loading spinner. List and mosaic covers decode at about 480px on the long side and share a disk cache of 1,000 objects kept for 90 days. Detail keeps the full image. The decoded-bitmap cache is capped at 200 images and 100 MiB. A shard whose server and cache reads both fail queries `temples` where `state` equals that state. Zero documents from that query is the same gap as a failed query: the state is not dropped. The bundled sample for the state is used in either case, and the screen says it could not load the state and is showing the offline sample. A state with no sample shows "Could not load temples in …" instead of disappearing. The detail screen says the page may be out of date when that document was read from the cache. An admin save with no coordinates writes null, not 0,0. `scripts/index_read_count.test.js` runs in its own emulator on project `demo-temple-index-reads`. The index cover is the first verified gallery image. `coverThumb` uses a stored `photos[].thumbUrl` when that photo is the cover, then a Wikimedia thumb rewritten to 480px. A Commons original `upload.wikimedia.org/wikipedia/commons/<h>/<hh>/<name>` becomes `.../thumb/<h>/<hh>/<name>/480px-<name>` when `<h>/<hh>` match the MD5 of the underscored filename. An SVG thumb appends `.png`. Anything else stays the full URL. It does not invent a Storage sibling. `scripts/clear_placeholder_covers.js` is dry-run by default. It removes placeholder-host URLs from `imageUrl`, `images`, and `photos` so the temple shows Photo pending. `--apply` re-reads each document in a transaction and writes that temple's index entry from the fresh document. CI cannot apply it. `scripts/resize_cover_thumbs.js` is dry-run by default. It lists each Wikimedia original that stays full size, and each Storage cover with no matching `photos[]` entry as `no-photo` (those are not uploaded, and no new top-level field is added). `--apply` writes the `_480_g{generation}` object in the cover URL's bucket with `ifGenerationMatch: 0`, checks the Firebase download URL (`?alt=media` and the stored token), and only then stores that URL on `photos[].thumbUrl`. The resume file is rewritten after each successful row and stores the cover URL. `--resume` processes a recorded temple again when its cover differs from that URL. A download check that is not HTTP 200 logs the storage object path and does not log the token URL. Each successful row is one transaction: re-read the temple, skip the row when the cover photo changed, set `thumbUrl` only on that photo of the fresh document, and write that temple's index entry from the fresh document. The index is not batched at the end of the run. A card whose cover is a Wikimedia 480 thumb falls back to the original file when that thumb fails. `--limit` and `--resume` bound the run. CI cannot apply it. It does not deploy. An admin upload re-encodes the full-size photo as JPEG at quality 80 before storing it, so GPS EXIF from the picked file is not in the public object. `scripts/audit_coords.js` is dry-run by default and prints the latitude and longitude it would discard. `--apply` re-reads each document in a transaction and nulls both coordinates only while they are still unpaired. Run it before deploying the paired-coordinate rules. An update that does not change latitude or longitude is allowed even when the stored pair is unpaired. A lithograph caption is stored on the entry. Latitude and longitude are both null or both numbers once that audit has been applied. The address kept for search is the leading 340 characters on a word boundary, so a comma inside that window does not drop the following words. `test/temple_service_index_test.dart` asserts the launch server-read counts. `scripts/index_read_count.test.js` counts the same shape on the local emulator.

Unit and widget tests run with `flutter test`. GitHub Actions workflow `analyze-test` runs on every pull request (no path filter) and on pushes to `main`. It runs `node --test scripts/state_batch.test.js scripts/rebuild_index.test.js scripts/resize_cover_thumbs.test.js scripts/audit_coords.test.js scripts/backfill_cover_photos.test.js scripts/clear_placeholder_covers.test.js`, `node --test scripts/photo_patch.test.js`, the Firestore emulator rules suite `scripts/temple_index_rules.test.js` (local emulator only, project `demo-temple-index`), and `scripts/index_read_count.test.js` in a separate emulator on project `demo-temple-index-reads`, then `flutter pub get`, `flutter analyze`, and `flutter test`. Those node steps check the state-batch validator, the temple index rebuild plan, the cover-thumb resize plan, and the dry-run photo patch tools. They do not pass `--apply` and they do not write production Firestore. **KAN-90 required checks are `analyze-test` only.**

Workflow `android-smoke` has no `push` trigger. A push trigger that would run smoke after three merges was not added. Smoke runs at 10:00, 17:00, 22:00, and 05:00 IST (`30 4,11,16,23 * * *` UTC) and via `workflow_dispatch`. The schedule stays four runs a day. It also runs on a pull request that has the `run-smoke` label. The workflow listens for `pull_request` types `labeled` and `synchronize` only. The emulator job runs when `contains(github.event.pull_request.labels.*.name, 'run-smoke')`. On a `labeled` event it also requires `github.event.label.name == 'run-smoke'`, so adding a different label does not start smoke. A `synchronize` event (a new push) starts smoke only while `run-smoke` is already on the pull request. Opening a pull request does not start smoke. Add the label with `gh pr edit <number> --add-label run-smoke`. After a green pull-request smoke, a follow-up job removes `run-smoke` so a later push does not start another run. That job's only permission is `pull-requests: write`. If the token cannot remove the label, the job warns and leaves it in place; remove it manually with `gh pr edit <number> --remove-label run-smoke`.

For a `pull_request` event the plan job skips the green/failed SHA check and always runs the emulator. On the schedule, the first job reads the Actions API for `android-smoke` runs on `branch=main`. It skips the emulator when `main` HEAD is already the last successful job's `head_sha`, and also when HEAD is the last failed attempt, so a red main is not retried on every schedule slot. A `failure` conclusion counts. A `cancelled` conclusion counts when that run was triggered by `schedule`, because a job that hits `timeout-minutes` is `cancelled`. A `workflow_dispatch` cancel does not count. `workflow_dispatch` always runs the emulator. The emulator job `timeout-minutes` stays 15. Setup usually takes about 6 to 7 minutes, so that job limit fires before the 12-minute shell timeout and the job is `cancelled`. The job's first step writes `JOB_START_EPOCH` to `$GITHUB_ENV`. The Maestro command is `timeout --kill-after=30s 12m bash scripts/ci/run_android_smoke.sh`. Screenshot capture is skipped when 600 seconds or more have passed since `JOB_START_EPOCH`. Otherwise its timeout is `min(180, 780 - elapsed)` seconds, with `--kill-after=10s`. PNGs already written are copied after that timeout, so a killed flow still uploads the shots it finished. A non-zero screenshot status does not fail the gate. Martand Sun Temple and Jejuri Khandoba Temple are captured before the other detail pages. `$SECONDS` is not the screenshot clock; it starts only when the smoke script starts, after the APK build. Gradle is cached with `actions/cache`. The key hashes `android/**/*.gradle*`, so the demo suffix in `android/app/build.gradle.kts` changes the primary key without changing dependencies. `restore-keys: gradle-` restores the previous Gradle cache on that miss. NDK side-by-side `28.2.13676358` is cached at `/usr/local/lib/android/sdk/ndk/28.2.13676358`. `demo-seed-launch` replaces the committed `-Xmx8G` Gradle heap with `-Xmx3g` on the runner before the release build, and caps the Kotlin daemon at `-Xmx1g`. `android/gradle.properties` stays `-Xmx8G` for local builds and for the android-smoke profile build. The profile daemon does not fill this runner; a 3g cap stretched that build enough to cancel the 15-minute job. Both jobs stop the Gradle and Kotlin daemons before the emulator starts. The pub cache is cached by `subosito/flutter-action` (`cache: true`). The AVD snapshot and the API 34 `google_atd` x86_64 system image are cached with `actions/cache/restore` and `actions/cache/save`, following the reactivecircus/android-emulator-runner pattern: on an AVD cache miss, boot once to save a snapshot, then run smoke with `-no-snapshot-save`. The save steps use `if: always()` so a failed job still stores a cold image. A cancelled job does not reach them.

Concurrency uses one group per pull request (`pr-<number>`) and `${{ github.ref }}` for every other event. `cancel-in-progress` is true only when `github.event_name == 'pull_request'`. A new push on a labelled pull request cancels that pull request's in-progress smoke. Pushes to `main`, the smoke schedule, and manual dispatches are not cancelled.

If the smoke job or the skip/plan job fails on `schedule` or `workflow_dispatch`, the workflow opens one issue labelled `smoke-failure`, or adds a comment when that issue is already open. A `pull_request` run does not open or comment on that issue, even when smoke fails. Setup usually takes about 6 to 7 minutes, so the 15-minute job limit fires before the 12-minute shell timeout and the job is `cancelled`. A scheduled run that is `cancelled`, including a job-limit timeout and a manual cancel of that scheduled run, posts the same way and counts as the last failed SHA. A manually cancelled `workflow_dispatch` run does not post and does not block the next scheduled retry. The comment lists commits between the last green SHA and the failing SHA, plus links to the run and the `maestro-debug` artifact. It does not rewrite the existing issue body. `issues: write` is granted only on that job. The plan job has `actions: read` only. Workflow permissions stay `contents: read`.

`analyze-test` and `android-smoke` do not sign a Play bundle or upload to App Distribution. The tester pipeline is [`demo-app-distribution`](#demo-apk-on-firebase-app-distribution), below.

A weekly workflow, `actions-minutes`, sums this repository's minutes for every workflow the Actions API lists, including `ci.yml` (`analyze-test`), `android-smoke.yml`, `demo-seed-launch.yml` (release build plus emulator, 40-minute job limit), and `actions-minutes.yml` itself. Disabled and deleted workflows stay in that list. The total is compared with the 2,000 free private minutes. Those 2,000 minutes are shared across the account. Other repositories use the same quota and are not included in this total. Minutes come from each job's `started_at` and `completed_at` on the Actions jobs API (`per_page=100`, `filter=all` so re-run attempts count), rounded up to a whole minute, with a 1-minute minimum for every job that ran. The workflow list and the run list use `per_page=100`. Runs use `status=completed`. Skipped jobs, and any job with no `completed_at`, are not counted, so an in-progress run does not fail the check. The check fails if that API errors, or if the workflow list is empty. A total of 0 is an error only when a non-skipped job actually finished. Workflows whose runs were all skipped, such as unlabelled pull-request smoke, are not an error. It does not call the run timing API or `/settings/billing/usage`. It opens or updates an issue labelled `actions-minutes` when this repository's minutes are at or above 1,500. The issue says this repository's minutes, notes that other repositories share the quota, and says: change the android-smoke cron to two runs a day, 10 AM and 10 PM IST (cron `30 4,16 * * *`). The workflow cron stays `30 4,11,16,23 * * *` (four runs a day) until that change is made.

`scripts/build_play_aab.sh` refuses to build unless the `android-smoke` job has succeeded on that exact HEAD SHA (`GH_TOKEN`, `GITHUB_TOKEN`, or `gh auth token`), and it refuses when `git status --porcelain` is non-empty. A `pull_request` smoke run does not count. Those runs carry the PR head SHA, not the merge ref. A schedule or `workflow_dispatch` run on that exact SHA still counts. The only bypass of the green-smoke check is exactly `SMOKE_GATE_OVERRIDE=1`, which prints a loud warning and continues. `0` and any other value are not a bypass. The override does not bypass a dirty tree. There is no release workflow; the script is the release gate. Do not set the override for a Play upload unless you accept an unsmoked commit.

## Maestro locally

The flow in [`.maestro/read_only_smoke.yaml`](../.maestro/read_only_smoke.yaml) is read-only against the production Firebase project baked into the app. If Firestore is empty or unreachable, the app falls back to the bundled sample temples. **Do not tap Seed, Admin sign-in, or Admin Panel.** Those write, or can write, and CI never runs them.

What it checks:

1. A fresh launch (`clearState`) shows the Terms and Privacy gate. The flow taps the accept button by id `policy-accept-button` before Home. Back is not used; that exits the app.
2. The app then draws Home (`Temple Directory` is on screen).
3. Browse opens a list that shows temple cards.
4. Search for `Meenakshi` shows Meenakshi Amman Temple.
5. Opening that card reaches temple detail.
6. **Get Directions** leaves the app. Maps, a browser, or an Android chooser all count. The button still being on screen fails the flow.

Install [Maestro](https://maestro.mobile.dev/) and start an Android emulator (API 30 or newer; CI uses API 34 `google_atd` x86_64, Pixel 6, userdata `2048M` via `-partition-size 2048`, and 4 cores when `nproc` is at least 4). This repo's hosted runner has 2 cores, so the job uses 2. The system image's `userdata.img` is about 7372 MB and neither `disk.dataPartition.size` nor `-partition-size` lowers what qemu allocates for Pixel 6. AVD prep replaces an oversized image with a 512M ext4 filesystem, then deletes the NDK and Gradle caches when those caches hit, so the 7372 MB allocation fits. The emulator needs something that can open `https://www.google.com/maps/...` (Chrome or the Maps app). Without that, Get Directions stays in the app and shows "Couldn't open directions on this device."

```bash
flutter pub get
flutter build apk --debug --dart-define=DEMO_BUILD=true
adb install -r build/app/outputs/flutter-apk/app-debug.apk
maestro test .maestro
```

`DEMO_BUILD=true` forces Google's test ad units. Debug builds already use those units; the define keeps a later release or profile smoke build on test units as well. CI builds a profile x86_64 APK so the emulator reaches the first Flutter frame sooner than a debug build. That profile manifest turns Impeller off; release builds keep it. The emulator uses `-no-audio -no-boot-anim -gpu swiftshader_indirect` with animations disabled. `google_atd` keeps Play services and omits the launcher and System UI. The system-image cache key is `system-image-android-34-google_atd-x86_64` and the AVD snapshot key is `avd-34-x86_64-google_atd-pixel6-snapshot`. Wait is tapped on `Process system isn't responding`, `Pixel Launcher isn't responding`, `System UI isn't responding`, and `Google Play services isn't responding`, including a dialog that names `com.google.android.gms`. Any other isn't-responding dialog, including one from this app, fails the job. The smoke script waits for `sys.boot_completed`, installs the APK with adb, and Maestro relaunches up to twice if `policy-accept-button` or `Temple Directory` is not visible within 60 seconds. Each relaunch clears app data, so the flow taps the accept button again before it looks for Home.

A profile build without admin tools is:

```bash
flutter build apk --profile --dart-define=DEMO_BUILD=true
```

Do not pass `ENABLE_ADMIN_TOOLS` for this flow.

## Demo-seed release launch

Workflow `demo-seed-launch` builds the APK Sanu installs:

```bash
flutter build apk --release \
  --dart-define=DEMO_BUILD=true \
  --dart-define=ENABLE_ADMIN_TOOLS=true
```

It uses the same `run-smoke` label gate as `android-smoke` (`pull_request` types `labeled` and `synchronize`, plus `workflow_dispatch`). The job signs with an ephemeral keystore (`android/key.properties` and `*.jks` stay gitignored). It is not the Play upload key. The script installs that release APK on the same API 34 `google_atd` emulator, expects the Terms gate, taps Accept, opens the Admin sign-in panel, and never taps Seed. Accept does not seed: Home reads Firestore and falls back to the bundled 180 sample temples in memory. It then turns the radios off, clears app data, and expects the gate again. Artifacts are `demo-seed-launch` (logcat and screenshots) and `demo-seed-apk`.

## Demo APK on Firebase App Distribution

Workflow `demo-app-distribution` builds the tester APK on every push to `main` and from **Actions → demo-app-distribution → Run workflow** (`workflow_dispatch`). From a checkout:

```bash
gh workflow run demo-app-distribution.yml --ref main
```

The build is the same release defines as `demo-seed-launch`, plus `DEMO_APP_ID_SUFFIX`:

```bash
flutter build apk --release \
  --target-platform android-arm,android-arm64,android-x64 \
  --dart-define=DEMO_BUILD=true \
  --dart-define=ENABLE_ADMIN_TOOLS=true \
  --dart-define=DEMO_APP_ID_SUFFIX=true
```

`DEMO_APP_ID_SUFFIX` (or Gradle `-Pdemo_suffix=true`) sets `applicationIdSuffix` `.demo`, so the installed package is `com.shradhaventures.temple.demo`, and the launcher label is `Temple Directory India Demo`. Only this workflow sets that flag. `DEMO_BUILD` alone does not. `android-smoke`, `demo-seed-launch`, and the Play AAB stay on `com.shradhaventures.temple` and `Temple Directory India`. On Android, a build with the suffix initializes Firebase from the `google-services.json` client for `com.shradhaventures.temple.demo`. Smoke and seed-launch keep the Play app id in `firebase_options.dart`.

That is a universal APK (armeabi-v7a, arm64-v8a, and x86_64). The job logs the file size. If the universal APK is over 60 MiB (62914560 bytes) it builds again with `--split-per-abi` and distributes those APKs instead. This command is `flutter build apk`. It does not call `scripts/build_play_aab.sh`, and those defines never go into the Play bundle.

A push to `main` starts the workflow only when it touches `lib/**`, `android/**`, `assets/**`, `pubspec.*`, or `.github/workflows/demo-app-distribution.yml`. `workflow_dispatch` still runs on any commit.

The job signs with the demo keystore from `DEMO_KEYSTORE_B64` (PKCS12, `storeType=PKCS12` in the gitignored `android/key.properties`). That key is not the Play upload key. The workflow decodes it to a temp file, and deletes the file and `android/key.properties` after the build. A device that already has a Play-signed install must uninstall that install first; Android will not replace it with a build signed by the demo key.

The APK is the `demo-apk` artifact, kept for 7 days. Distribution runs `firebase appdistribution:distribute` (firebase-tools 15.34.0) with `--groups core-testers`. Release notes are the 7-character SHA, the commit subject, and the Actions run URL. A `pull_request` run, or a run missing the demo keystore or App Distribution secrets, skips distribution and succeeds. The job does not install the APK, open Admin, tap Seed, or write to Firestore.

Testers install it from App Distribution:

1. In the Firebase console, open project `temple-directory-india` → App Distribution → Testers & Groups. The group alias is `core-testers`. Add the tester's Google account email. Firebase sends an invitation.
2. The tester opens that invitation and accepts it.
3. On the phone, install **App Tester** (the Firebase App Distribution app) from the link in the invitation, or from Google Play under the name App Tester.
4. Sign in to App Tester with the invited Google account.
5. Open Temple Directory India, choose the latest build, and install it. Android may ask for permission to install from App Tester.

The service account in `FIREBASE_APP_DISTRIBUTION_SA_JSON` needs the **Firebase App Distribution Admin** role (`roles/firebaseappdistro.admin`) on `temple-directory-india`, and the Firebase App Distribution API must be enabled. It does not need Firestore access. `FIREBASE_ANDROID_APP_ID` is `1:109314154382:android:856cbde1eb92ba234ccedf`, the Firebase Android app id for `com.shradhaventures.temple.demo`. That is not the Play app id in [android-play-internal-test.md](android-play-internal-test.md). Before distribution, the workflow compares the secret to that id and fails without printing the secret if they differ. `analyze-test` runs `scripts/ci/test_demo_distribution_guard.sh` and still runs `scripts/test_play_aab_guard.sh`.

`android/app/google-services.json` includes that `.demo` client next to the Play client (`com.shradhaventures.temple`) and the legacy `com.example.temple_app` client. `scripts/ci/check_demo_google_services.sh` fails the demo build if the `.demo` client is removed or its `mobilesdk_app_id` or `api_key.current_key` is empty. Leave the Play client in place.

## Demo ads (`DEMO_BUILD`)

`--dart-define=DEMO_BUILD=true` makes `AdHelper` banner and interstitial ids the official Google test units in every mode, including release. KAN-89 is this `DEMO_BUILD` define. There is no `USE_TEST_ADS` define. The Android AdMob application id becomes Google's test app id `ca-app-pub-3940256099942544~3347511713` when Gradle sees `DEMO_BUILD` (Flutter passes it as `-Pdart-defines`). Otherwise Gradle supplies the production Android app id. The main manifest does not hard-code either id: `android/app/src/main/AndroidManifest.xml` sets `com.google.android.gms.ads.APPLICATION_ID` to `${admobAppId}`, and `manifestPlaceholders.admobAppId` in `android/app/build.gradle.kts` fills that placeholder. Test units still show the Test Ad label with the production app id; that is the same pairing debug builds already use.

iOS unit ids follow the same Dart rule. The iOS application id in `ios/Runner/Info.plist` stays the production value.

`scripts/build_play_aab.sh` refuses `DEMO_BUILD` and `ENABLE_ADMIN_TOOLS`, a bundle signed with `CN=Android Debug`, a dirty working tree, and a HEAD SHA that does not have a successful `android-smoke` job from `schedule` or `workflow_dispatch`. A `pull_request` run does not count. Exactly `SMOKE_GATE_OVERRIDE=1` bypasses only that smoke check, and it prints a loud warning. CI does not have the Play upload key, so `analyze-test` runs `scripts/test_play_aab_guard.sh` instead of building an AAB. Signing setup is in [android-play-internal-test.md](android-play-internal-test.md).
